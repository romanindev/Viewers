## Tools used

- Claude Code — implementation assistance inside the repository.

## How AI was used

### Planning

ChatGPT was used up front, before any code was written, to:

- extract requirements from the supplied test-task PDF;
- compare repository strategies;
- draft an initial `postMessage` contract and PR-by-PR implementation plan.

That draft plan was then checked against the actual checkout in a
read-only Phase 0 audit (`IMPLEMENTATION_PLAN.md` "Phase 0 — Baseline
verification") before any feature PR started, which is where several
of the draft plan's assumptions were found to be wrong (see the
examples below).

Claude Code was used inside the repository for the implementation
work itself: writing the host app, the shared message-contract
package, the viewer-side bridge extension, and the documentation
files (`ARCHITECTURE.md`, `IMPLEMENTATION_PLAN.md`,
`docs/scoring-form/*`), iterated PR by PR against the running
apps and, where noted below, against browser-observed behavior.

## Verification policy

AI output is not treated as authoritative for OHIF internals.

Before accepting AI-generated OHIF integration code, the implementation is checked against:

- the actual forked OHIF source;
- the actual selected OHIF version;
- browser behavior with a real study;
- actual `measurementService` event payloads.

## Concrete review decisions

These are the concrete cases, backed by `IMPLEMENTATION_PLAN.md` and `ARCHITECTURE.md`, where an initial plan or implementation was revised against the actual source or against observed browser behavior:

- **Activation requires read-back verification.** `extensions/cornerstone/src/commandsModule.ts:1214-1228` shows `setToolActive` fails silently on error. The activation flow (PR 4) was implemented to read back `toolGroup.getActivePrimaryMouseButtonTool()` after calling `setToolActiveToolbar`, and only arms a row if that read-back confirms `EllipticalROI` is active — otherwise it sends `ACTIVATION_FAILED`. A caller that trusted `setToolActive`'s return value alone would silently arm a row that never actually activated.
- **The default tool is `WindowLevel`, not `Pan`.** The initial plan assumed the baseline primary tool to restore after a cancel/completed measurement was `Pan`; the Phase 0 audit found the actual default in `modes/basic/src/initToolGroups.ts:20-37` is `WindowLevel`. The restore path was implemented against the fixed `WindowLevel` constant, not a captured-and-restored "previous" tool.
- **`cachedStats` is not final at drawing completion.** PR 5 initially treated the area value as settled as soon as OHIF's drawing-completion event fired. Manual observation showed it can still change afterward — one recorded draw reported `4214.7176 px²` at `MEASUREMENT_ADDED`, then `26601.9840 px²` in a `MEASUREMENT_UPDATED` 51 ms later, matching OHIF's own displayed value. The implementation was reworked to a 200 ms settle-and-replace debounce per `measurementId` before sending the final value to the host, documented as an MVP heuristic rather than a finality guarantee (`ARCHITECTURE.md` §10.12).
- **Totals preserve exact units and full precision.** `computeTotals` (PR 6) groups strictly by the exact unit string, so `mm²` and `px²` (and calibrated suffixes) are never summed together, and it sums unformatted values — `.toFixed(2)` is applied only at render time, not before summation — so rounding a per-row display value can never distort the total.

## Responsibility

All submitted code is reviewed and understood by the author.

The author must be able to:

- explain the message protocol;
- explain correlation IDs;
- explain handshake/queue behavior;
- explain cleanup;
- change the tool live;
- add a measurement field through the whole chain;
- diagnose a broken handshake.
